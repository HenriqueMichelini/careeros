## P2: preserve pending work across session transitions

**Cause:** account/workspace identity included session expiry. A same-account replacement remounted the store, and an unauthenticated probe unmounted the only pending-work copy. The actual Chrome probes reproduced both losses before any production source edit. Explicit logout also offered no pending-work disposition.

**Repair:** workspace identity follows the verified account, independently of session expiry. Authentication loss/account change disposes that client's request lease and removes its workspace from the UI; it does not discard its pending request. Same-account reauthentication can resume it, while prior-lease replies cannot mutate or clear newer work, including after returning to the same account. Different accounts use different clients/stores and never display or replay each other's recovery.

Only the frozen pending Profile Save request (operation ID, expected revision, candidate document), its account ID and format version are checkpointed under `careeros_pending_profile_v1:<accountId>` in tab `sessionStorage`. This is an untrusted recovery/editing copy, **not** account authority or a confirmed saved Profile. No session/CSRF/provider tokens or BYOK credentials are included. No legacy key is read or transferred. Reconstruction first requires a fresh authenticated account probe and successful protected Profile read; only then is pending wording shown with its uncertain state. A failed server read does not use the checkpoint as authority. Reauthentication/reload never automatically retries a mutation; deliberate retry preserves the exact original bytes/base/operation identity.

Logout with pending recovery offers download, cancel, keep recovery in this tab, or discard recovery and sign out. Discard/confirmed Save clears the checkpoint when storage permits; discard invalidates older continuations and never claims to undo a server write. A missing outcome read no longer silently discards a failed pending request. Storage failure retains memory recovery and reports the limitation. When pending work exists, sign-in opens another tab so the original tab can stay open until the person returns after sign-in. Only the submitted Save candidate is checkpointed: unsubmitted form text, arbitrary component state, proposals and credentials are not persisted across an application reconstruction.

**Permanent regressions:** `tests/account-session-browser.check.mjs` runs actual React/Chrome replacement, natural frontend expiry/reauthentication and lifecycle cases. They assert retained pending wording, signed-out and B-account isolation, no automatic PUT, identical recovery identity, logout cancel/keep/discard and a reconstructed application using only the synthetic server fixture plus the real tab checkpoint. Existing actual-browser account-switch/late-response and EN/PT checks pass. Three added client contract tests cover checkpoint reconstruction/scoping, old request leases after same-account resume, failed checkpoint storage, explicit discard and no server-authority fallback.

## P2: reject initiating-session expiry during account-lock waiting

**Cause:** PostgreSQL `Sessions.Create` compared expiry against caller time captured before waiting for account locks. The real-engine independent overlay started replacement while valid, held the account lock across natural expiry and observed successful insertion after expiry.

**Repair:** after the common sorted account locks are obtained, both initiating-session validation and its atomic removal predicate use current database `clock_timestamp()`. Transaction-start `now()` and the caller's captured clock are not authority. The common account-before-session lock order, active status/generation checks and atomic removal/insertion contract are retained.

**Permanent regressions:** `internal/accountapi/session_replacement_test.go` checks initial validity, observes actual lock blocking and natural database expiry before releasing the lock, then independently expects `ErrInvalidTransaction` and no replacement row. It also exercises valid replacement despite a deliberately incorrect caller clock, both actual logout/replacement orderings through two stores, another device, unchanged authorization generation and fresh sign-in. Deterministic trigger/advisory-lock gates establish each ordering, with no fake database.

The corrected recovery guarantee is deliberately bounded. A tab checkpoint can be unavailable, cleared or restored by browser/session behavior; it is not a secure archive, cross-device recovery, server authority or a zero-data-loss guarantee. Memory recovery requires keeping the original tab open. Checkpoint removal failure may retain a stale recovery copy, which still cannot authorize access/replay. Explicit discard cannot cancel a previously sent/committed Save. No server retention/replay horizon, backup/restore target or production policy is selected here.
