### What diagnostics actually retain

All five routes are wrapped in `aidiagnostics.Workflow`. Each normal handler return emits one request-local attempt to the default Go log sink, or an injected in-process sink in evaluation. It contains `version`, random 128-bit hexadecimal `attemptId` (empty if entropy acquisition fails), `workflow`, `outcome`, `httpStatus`, `durationMs`, `applicationResultReuse`, `stages`, and nullable `accepted`. There is no client attempt-ID response header/body field or ingestion endpoint for browser outcomes. The wrapper does not defer emission around panic/termination, so absence of a record is not proof that no attempt happened. [D1]

Each stage contains `name`, code-owned `version`, `outcome`, `durationMs`, and optional `provider`. Provider metadata contains `name`, allowlisted `returnedModel`, nullable `inputTokens`, `outputTokens`, `reasoningTokens`, `prefixCachedTokens`, nullable `outputTokenCeiling`, `durationMs`, `httpStatus` and `completion`. No provider request IDs, source text, credentials, source hashes, fact IDs, URLs, document names or user IDs are accepted by this schema. Labels are strings whose safety depends on audited constant/enum callers; this is not a general-purpose redaction system. Go's log prefix also adds wall-clock time. [D1] [D3]

Missing or malformed token metadata remains null, independently of valid output. Offline summaries separately count available/unavailable requests, require exact-model dated caller-supplied prices, include priced failed attempts in cost numerators, and leave unpriced totals/billing unavailable. Reasoning tokens are a subset of output; cached tokens are a subset of input. `accepted` requires external evidence and is never assigned in production; `applicationResultReuse` has no assignment and defaults false. Neither is a measured browser outcome today. [D2] [D4]

The production sink writes per-attempt JSON to process/platform logs. It has no repository-defined central database, dashboard, bounded log buffer, rotation, retention, deletion or access policy. `WithSink` is request-scoped in-process capture, not persistent collection. `scripts/ai-diagnostics` aggregates supplied JSON offline or runs synthetic controlled transports; it is not an operational log collector or browser export UI. Availability after a stateless invocation depends on hosting log collection, which was not verified here. Existing release reports include bounded dated log checks, not a universal no-content guarantee for infrastructure. [D1] [D4] [E4]

### Lifecycle and attribution findings

Use separate technical, domain and user outcome axes; a single expanded success boolean cannot represent these boundaries.

| Current meaning | Limitation | Proposed interpretation |
| --- | --- | --- |
| HTTP 200 | May be Jev rejection, incomplete ingestion, support unavailable, or review-blocked Draft. | Transport result only. |
| Diagnostic `completed` | Normal handler/stage return with no recorded non-completed stage; says nothing about user review/save or truth. | Backend technical completion. |
| Draft review `complete` / `unavailable` | `complete` is currently counted as diagnostic failure; availability is independent of whether every statement is supported. | Provider/check execution outcome separate from domain assessment. |
| `invalid_output` → `rejected_output` | Provider envelope causes may override stage result; post-stage validation may fall back to generic `input_rejected`. | Retain safe categorical error cause and origin, without provider message text. |
| Jev irrelevant/unusable/rephrase/clarification/attack decision | Policy decision may use HTTP 200; treating all non-completed outcomes as operational failure inflates outage rates. | Policy category separate from provider failure and user rejection. |
| Client `stale`, `aborted`, save failure | Backend may have completed or seen transport failure/timeout; cancellation is not necessarily observable there. | Client-owned outcome; backend status remains independent. |
| Retry / reuse | New request gets a new backend ID; a local hit may make no request. Current reuse boolean is not populated. | Explicit bounded session-local action; no inferred retry from similar content. |
| Saved / accepted / support current | Save means durable browser write; acceptance means a specific deliberate choice; current means matching source revisions. | None implies truthful facts, semantic equivalence, exhaustive recall or employer submission. |

Backend attempt duration includes handler preparation, validation, providers and response work. Stage durations overlap: reconciliation includes candidate retrieval, and generation can include support checks. Do not sum stage durations into end-to-end latency or subtract their sum from attempt duration. Provider timing includes the observed HTTP/body path; it is not pure model inference time. Browser review waiting, user typing, saving, network transfer and employer actions are outside backend duration. A future local summary should keep active processing, review wait and durable save distinct, using monotonic elapsed time and coarse buckets for export. [D1] [B1] [A2]

### Correlation and counting contract for a future local slice

Keep today's server-generated random ID per HTTP request. Do not repurpose Profile/fact IDs, source hashes, job-context identity, Apply-answer provenance or credentials as diagnostic correlation. Each explicit browser action could have an ephemeral in-memory random ID and at most one local terminal outcome, with bounded stage/request ordinals. If Henrique chooses backend/client joining, return a server-generated ID in the response and associate it only in memory; missing responses leave correlation unavailable. Do not accept arbitrary client IDs into server logs or introduce a stable browser identifier. Joining exposes linkage and needs an explicit decision; the smallest initial slice can omit it.

Parallel actions must remain independent. A deliberate retry receives a new action/request identity and preserves the first failure; an optional ephemeral parent link stays local. Distinct artifact decisions must not count as multiple workflow successes. Deduplicate repeated terminal transitions within the capped in-memory summary, not by source content. Cancellation after a successful server return can produce backend completed plus client canceled/obsolete; preserve both facts. Observation must not alter transaction idempotency, bypass revision checks, retry user data, block offline work or change save/accept state. Export failure is a diagnostic delivery failure only.
