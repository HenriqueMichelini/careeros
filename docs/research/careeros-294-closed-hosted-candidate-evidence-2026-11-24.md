# CareerOS #294 closed hosted candidate evidence

**24 November 2026 · America/Sao_Paulo · planning evidence.** The October #261 decision selected Cloud Run and Neon in São Paulo as the research reference. The later #294 owner decision selects Cloud Run and Neon Launch in São Paulo for local candidate preparation. The configuration proposed for review is one isolated Cloud Run service using its default HTTPS origin and one isolated Neon Launch project using direct TLS PostgreSQL. This proposal depends on demonstrable application-level admission and logging controls, and on approval of a public database endpoint and public web ingress for the synthetic environment. Keep an external load balancer and Neon Scale as separately priced options if the owner requires edge filtering or database IP allowlisting. Public documentation was refreshed for this note. Account entitlements, deployment, capacity, prices charged and observed recovery remain unverified. The #295 recovery exercise requires its own pinned configuration and authorization. ## Database, backup and exclusion

- **Launch** is a paid usage plan with up to seven days of PITR history, scheduled snapshots, five-minute idle suspend that can be disabled, and three days of in-console metrics/logs. **Scale** has up to 30 days of PITR and 14 days of metrics/logs, plus IP Allow and private networking features. **Free** has up to six hours/1 GB of history, one manual snapshot and no scheduled backups. Choose based on exact required controls and retention, independently of the local test archive age. Neon documents shared 0.25 CU compute with 1 GB RAM. Cold wake, working-set and cross-cloud fit require a hosted receipt. [Current plans](https://neon.com/docs/introduction/plans) · [Compute sizes](https://neon.com/docs/manage/computes)
- Give the closed candidate its own synthetic Neon project, OAuth client, cloud project/service account, artifact and secret inventory. Use a further separate quarantined Neon project for the older-copy drill. Project separation provides distinct databases/endpoints and separate project permissions within an organization. Check organization admin access and API keys that still span projects. Use the project ID and database role inventory to verify isolation because Neon can name the default root `production` even for a synthetic project. Keep only PostgreSQL enabled for CareerOS and explicitly verify the Data API is disabled. Create narrow runtime and observer roles via reviewed SQL because Neon Console default role provisioning grants elevated `neon_superuser` membership. Pin independent migrator, ledger, restore and administrative access. [Neon projects](https://neon.com/docs/manage/projects) · [Neon roles](https://neon.com/docs/manage/roles) · [Neon user permissions](https://neon.com/docs/manage/user-permissions) · [Cloud Run secrets](https://docs.cloud.google.com/run/docs/configuring/services/secrets)
- Neon Launch's public PostgreSQL endpoint uses TLS and DB authentication. It requires acceptance of the endpoint reachability for the closed drill. If allowed source IPs are mandatory, price Neon Scale and reviewed fixed outbound addresses for **every** required caller. Cloud Run default internet egress uses a dynamic shared pool. Direct VPC egress for all traffic plus Cloud NAT and reserved IP is Google's documented option. Test egress for approved Google, database and observation paths and prove zero actual AI provider sends with the hosted artifact and credentials. A provider budget or app admission stop cannot prove network isolation. [Neon plan controls](https://neon.com/docs/introduction/plans) · [Neon IP Allow](https://neon.com/docs/manage/projects#configure-ip-allow) · [Cloud Run static outbound IP](https://docs.cloud.google.com/run/docs/configuring/static-outbound-ip)
- Neon instant restore replaces branch state, creates an old-head backup branch and returns clients to the same connection details. It can revive older records and does not fence old writers. Native history/snapshots share the Neon project/region. For the separately approved #295 drill, use a pinned logical archive in isolated custody restored into a separate quarantined project, with roles/ownership/grants reapplied and verified by the reviewed procedure. A logical dump alone does not include the independent authority needed to recover later acknowledged content, revocations, deletions, deadlines, allowance/ledger and occupancy. Retain the five-minute age benchmark for the independently provable latest raw point and record the deliberately older copy age separately. Bound copy expiry, disabled schedule/cleanup, actual RPO and end-to-end RTO before execution. Neon can retain the most recent scheduled snapshot past its configured expiry while the schedule remains active. [Instant restore](https://neon.com/docs/postgres/backup-restore/branch-restore) · [Snapshot retention](https://neon.com/docs/guides/backup-restore#snapshot-retention) · [Logical restore](https://neon.com/docs/import/migrate-from-postgres) · [#295 local design decision](../hosted-restore-drill-design.md)
- For old-system exclusion, plan an observed combination of revoking old app/revision/runtime authority, stopping traffic and old writers and jobs, denying new old-role logins, terminating existing direct and pooled sessions, and accounting for privileged sessions, replicas and every alternate path before reopening. `pg_terminate_backend` requires the relevant privilege and positive termination confirmation. Neon limits the `neon_superuser` role's ability to terminate sessions of other elevated roles. Restarting compute interrupts connections, while suspended compute can be reactivated by a connection. Deleting approved disposable old endpoints can remove those connection paths and a recreated compute gets distinct connection details, but account admins can recreate resources. Verify non-reconnect, old pending/held work denial and old DB endpoint denial under control-plane access and recovery permissions. Entire project deletion has a seven-day user recovery path that can restore old connection strings and collaborators. Treat deletion as separately authorized and test it only if the frozen design selects it. [PostgreSQL session signal permissions](https://www.postgresql.org/docs/17/functions-admin.html#FUNCTIONS-ADMIN-SIGNAL) · [PostgreSQL role login](https://www.postgresql.org/docs/17/role-attributes.html) · [Neon role privileges](https://neon.com/docs/manage/roles#the-neon_superuser-role) · [Compute lifecycle](https://neon.com/docs/manage/computes#restart-a-compute) · [Deleted project recovery](https://neon.com/docs/manage/projects#recover-a-deleted-project) · [Cloud Run traffic rollback](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)

## Cost sensitivity and exact approval gaps

An illustrative attended #294 window uses one runtime, one DB, a **four-hour** window, **1,000 requests**, **1 GiB transferred** and **one positive fake-only opening**. The cost scenario assumes four hours of aggregate billed service activity including starts, shutdown and overlap, and four billed hours on the Neon endpoint. Public ingress can receive unrelated requests. The wall-clock end time alone cannot enforce aggregate billed instance time or public request counts. The example excludes a separate #295 restore project and its run. It assumes one Neon compute fixed at 0.25 CU, 1 GB live storage, 0.25 GB retained history and 1 GB billable snapshots, each storage quantity budgeted at a full month to illustrate residual-copy costs. Verify the byte volumes and actual lifetimes before setting spending and cleanup bounds.
