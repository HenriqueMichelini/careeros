## One authority and its boundary

Proposed `internal/aicontrol` owns the domain transitions and provider-specific accounting interface. PostgreSQL persistence composes with `internal/accountstore`'s existing transaction/owner checks; it does not run a separate check-then-write store. Existing OpenAI and TypeSafe adapters call a private dispatcher before every actual send. Workflow handlers declare the Action and stage; they cannot mint permits, choose arbitrary policy/provider endpoints or bypass accounting with a supplied client. No browser database access or exported reusable send token is introduced.

The future local slice includes the domain/store, additive local-test migrations, transport wrapper, adapter wiring and synthetic integration tests through the Go router and five Function handlers. Real managed egress has no enabled mode in the proposed slice. Existing BYOK behavior is not silently converted to centrally billed access; any compatibility path must remain explicit and must never obtain CareerOS-managed credentials. The current preservation scope is source behavior and quality contracts, not a live-provider test.

The module offers bounded commands, conceptually `OpenOrRecoverAction`, `ReserveDispatch`, `AuthorizeIntent`, `ObserveOutcome`, `ApplyEvidence`, `ReviewConservativeClosure`, `CancelAction` and `GetActionStatus`. These are internal contracts, not newly approved public APIs. One private method owns transport invocation. Recovery/lookup is read-only with respect to inference. A background worker may reconcile evidence or mark review eligibility; it must never resend an intent as an outbox job.

Production gateway/fence and recoverable-result authorities remain unimplemented dependencies. The fake implementation must make their absence explicit and reject managed egress/customer deduction. Do not substitute an always-true production stub.

## Identity and immutable binding

| Identity | Proposed invariant |
| --- | --- |
| **Action** | Server-issued opaque ID scoped to the verified account and admission namespace. One explicit business command: ingestion submission, section review, standalone CV, qualification analysis or Draft generation. It binds workflow/protocol version, validated effective inputs, Profile identity/revisions where relevant, job/temporary-answer snapshot, language, fixed prompt/schema/model/tier and policy identities. Generate another/optional rewrite creates a new Action. A changed payload under an existing key is a conflict. |
| **Stage** | Server-owned child of the Action with a fixed kind and coordinate: gate, batch/portion, assemble, reconcile focus, clarification revision, generation or support review. A stage graph fixes permitted parents and branch predicates. Provider-free stages are still replay-bound but have no invented expense. Caller-supplied stage names/cursors do not create authority. |
| **Attempt** | An explicit permitted attempt within a stage/Action. Network replay does not create one. Deliberate Retry of known failed/incomplete work with unchanged inputs may create a new bounded attempt only while the Action is recoverable. Unknown send status is not a known failure; terminal cancellation/closure cannot be retried into life. |
| **Dispatch** | Unique server-owned ID for one provider request within an attempt, including every TypeSafe gate. Reached subrequests have different IDs even if their input happens to match. Unique stage/attempt/leg coordinates make duplicate intent creation fail. One dispatch owns one maximum, one original intent time and one accounting contribution. Provider request IDs are supplemental evidence, never the local primary key. |

**Root creation has a no-send handshake.** Before the first create request, the caller freezes a bounded random creation key for that explicit command. A unique `(verified account, admission namespace, creation key)` record binds the root fingerprint and server-issued Action ID atomically. Create/recover performs no inference. A lost create acknowledgment is recovered with the same key: identical input returns the existing ID, changed input conflicts. Execution starts only with the acknowledged Action ID and the same immutable binding. The creation key is an idempotency coordinate, not a credential or ownership proof; it stays in the restricted replay scope. Losing it does not authorize automatic creation/generation under another key. Deliberately starting a new Action is independently admitted and bounded. Compaction/key retirement/namespace expiry must reject old creation commands as well as old execution commands.

Use a versioned, length-delimited canonical encoding of the validated effective request; preserve supported Unicode/opaque values and distinctions required by the existing contract. Do not trim/normalize away a material difference or include credentials. Proposal: account- and purpose-scoped **HMAC-SHA-256** with restricted key version, binding version and 32-byte value. Include the complete egress-affecting input/settings and source revisions, not just a Profile revision or client hash. Retain the HMAC, not its career-content preimage. This is linkable personal metadata, not anonymization or semantic verification.

The Action binds the root input/settings. Each stage additionally binds its exact effective request, parent-stage identities and authenticated handoff identity. Profile ingestion clarification can add an explicit protocol-defined child input; it cannot overwrite the original submission or an already-bound clarification. A second answer for the same child key conflicts; a deliberate new clarification creates a new child revision subject to its finite stage/attempt limits. No arbitrary changed-input Retry is permitted.

Freeze configuration for an admitted attempt. If a prompt/schema/model/rate policy has changed or expired so that the frozen maximum is no longer valid, do not silently reprice or reinterpret a replay: deny the new send and require the applicable explicit transition/new Action. Previous counted exposure remains. Existing outputs or signed client-held handoffs must still pass existing source/protocol checks. Signature/hash equality does not establish truth, semantic completeness or spend entitlement.

An identical duplicate returns the same safe state/receipt with **zero new sends and zero new customer effects**. If a completed stage's transient output is unavailable, report output unavailable; do not regenerate to reconstruct it. A conflicting duplicate fails before admission. After fingerprint-key retirement, missing binding evidence or compaction, deny unverifiable replay or return the preserved terminal status. Never reinterpret it as a fresh request.

These are logical records; exact table grouping is a routine implementation choice. Field types/roles are proposed for synthetic local verification, not permission to collect real metadata.

| Action/stage/attempt | Opaque owner/Action/stage/attempt IDs; fixed workflow/protocol/coordinate; parent reference; binding/key versions and fingerprint; state/CAS version; original authoritative times. Unique account/Action and stage/attempt/leg constraints. |

No credential, credential hash, headers, prompt or response body. |
| Scope allocations | Unique dispatch + scope + policy-period allocation, held/count contribution, carry obligation and version. Account/global/provider scopes reference the same obligation rather than duplicating charges. Period rollover does not drop unresolved exposure. |
| Restricted evidence/adjustment | Unique evidence/adjustment ID and dispatch; bounded provider-request identity when actually available; allowlisted model/tier; numeric usage with presence/validity and category version; rate identity; supported estimate or confirmed amount/currency; reason/actor/time and prior/new contribution. No raw envelope, invoice, provider error text or account export. |
| Minimal outcome/deletion/replay marker | Opaque namespace/Action/dispatch reference, terminal/deny disposition, necessary original clock anchors and deletion/exposure/replay version. Database constraints enforce positive finite maxima, supported currency/units, immutable bindings/intent anchors, unique logical dispatch and evidence IDs, and monotonic terminal dispositions. Use checked integer fixed-point amounts or exact decimals with explicit precision/ceiling rules; never binary floating point for admission. Reject overflow, unsupported categories/currency, unbounded input or an unavailable valid maximum. No default zero allowance, infinite grant or convenient rate is inferred.

Use one documented lock order: account, session, relevant grant/policy and Action/stage, then all financial scope rows in stable key order, then capacity rows in stable key order. Every competing admission/revocation/adjustment operation uses the compatible order and transaction contract. **After every potentially blocking lock is acquired, use a fresh DB-clock reading to recheck session, grant and policy expiry in the final write/intent-claim predicate.** A check before waiting, or a transaction-start timestamp reused after contention, is insufficient. SQL transaction retry is permitted only before external effects, with the same immutable IDs; it cannot retry the provider operation. Commit-acknowledgment uncertainty requires readback, not a new dispatch key.

## Reservation and authorization before every send

1. **Validate and recover.** The handler obtains the real session owner, applies existing Origin/CSRF/input/source/Profile gates and resolves the Action/stage binding. Read/replay produces no provider call. No valid configured policy or SQL authority means denial before a send.
2. **Reserve atomically.** In a transaction using current account/session authority, lock every applicable account/global/provider financial and capacity scope. Check grant/Action/stage/attempt/input/output-token ceilings and remaining limits. Create the unique dispatch reservation and all scope allocations together. No partial reservation or counter update may survive rollback. Reservation is per reached leg, not a promise that every later workflow leg will be admitted.
3. **Authorize durable intent.** Immediately before transport, repeat the current account/session/generation, grant, frozen policy, binding, relevant Profile-currentness and stop-state checks in the intent transaction. After all blocking locks, its final claim predicate rechecks expiry against a fresh trusted DB clock. It atomically claims the still-reserved dispatch, durably records that claim's original `intent_at`, consumes its bounded attempt allocation and records its possibly-sent maximum. The first send may combine steps 2/3 in one transaction. Later legs always run their own authorization; route-entry authentication is insufficient.
4. **Invoke once.** Only the known successful claimant receives a process-local, one-use permit. The private dispatcher invokes its fixed adapter at most once. It never returns a reusable send token or resumable job. A lost commit acknowledgment causes **zero invocations by that claimant**, while the durable intent is conservatively treated as possibly sent. Restart cannot reconstruct a permit.
5. **Observe and reconcile.** Record the bounded response/evidence and local/remote/financial observations idempotently. Parser failure, SQL failure after response or client disconnect cannot erase the committed obligation. Before returning any protected result, retain existing authorization/Profile-currentness checks; atomic durable result publication is a separate dependency.

**Authorization linearizes at the final intent-claim predicate, made durable by its successful transaction commit.** Revocation ordered before that claim denies the dispatch. Revocation ordered after it is after authorization; already authorized work may still reach transport or remain physically active. Time-based expiry after authorization has the same in-progress-work qualification; expiry during lock contention must be detected before the claim. Another unlocked revalidation before the socket call cannot eliminate that race. Logout/current account generation alone must never be described as an effective provider-dispatch fence. Stronger admission-close/dispatch-close semantics require a gateway that can invalidate/drain all not-yet-handed-off permits across processes and fence unreachable holders before acknowledging closure. The proposed local slice tests that boundary with a fake gateway; live gateway/fence proof remains a blocker.

Prohibit redirect following, automatic SDK/client/transport retries and fallback in the controlled path. Do not add an idempotency header assuming it makes provider execution once-only. Test actual adapter invocations and outbound attempts in the fake transport, including 307/308, connection resets and retriable statuses. At most one local invocation is the contract; exactly-once remote execution or wire delivery is not claimed.

A pre-intent reservation may be atomically abandoned/released only if it remains unclaimed and no sender can acquire it afterward. CAS/locking orders release against intent claim. After durable intent the conservative default is possibly sent, including a crash before any socket write. A lease, elapsed timeout or missing log never proves unsent. This intentionally sacrifices availability when certainty is unavailable.

## Provider accounting and reconciliation

For each dispatch let `M` be its valid reserved maximum, `E` its supported estimated/confirmed expense when available, and `R` its unreleased conservative admission floor. Its contribution to any applicable spending scope is **`C = max(E if known else 0, R)`**, not `M + E`. Initially `R = M`. The same dispatch contributes once within each applicable account/global/provider scope. All scopes update atomically; they are different admission views of one obligation, not independent provider bills.

Unresolved possible sends keep `R = M`. A supported usage/rate estimate is stored distinctly from a confirmed bill and never converted to zero or overwritten by M just because time passed. The default retains the residual floor until accepted evidence/adjustment authority permits reduction; an estimate alone does not silently create headroom. A reviewed reconciliation can set an evidence-supported floor/amount under its explicit evidence policy. That evidence policy and authorized operator roles are unresolved for production; the local suite supplies synthetic policies only.

After W, only a financially unresolved dispatch with no supported estimate/confirmed charge can undergo explicit reviewed conservative closure: change its accounting disposition to `reviewed_conservative_maximum`, preserve `C = M`, original clock, carry and replay protection. Record who reviewed it, the categorical evidence status, amount and policy version. Eligibility itself does nothing. Financially supported estimates/confirmed bills are excluded from this age-based conversion. Safe compaction is an additional purpose/retention decision, not a side effect of closure. The accepted trade-off is that late lower per-call attribution may become permanently unprovable and remain overcounted.

Provider adapters expose versioned billable categories and their relationships. Preserve field states `present`, `unavailable`, `invalid` or `unsupported`, with applicable model/tier/rate identity and currency. Cached input/reasoning or other subset categories cannot be added again to their parent totals. Cache-write or an unfamiliar category/tier cannot disappear because the existing diagnostics type lacks it. Provider-specific maximum computation must cover prompt/input, generated reasoning/output, cache-related categories, service tier and any applicable fixed request charge. If a valid finite upper bound cannot be justified, deny admission; an output-token cap alone is insufficient.

Reconciliation accepts only attributable evidence within the correct provider/billing namespace and dispatch coverage. Bounded provider-request IDs may be absent; absence stays explicit. Duplicate evidence IDs are idempotent, conflicting content under an existing evidence ID is rejected, and partial/reordered reports cannot overwrite stronger evidence or generate another adjustment. Aggregate invoice totals cannot become fabricated per-dispatch charges. Restricted evidence records contain no career payload or full invoices. Evidence-supported downward adjustments remain possible only while linkage/evidence and the separately authorized adjustment mechanism support them.

If credible expense exceeds M, retain the actual amount and an explicit maximum-breach state, increase counted exposure/carry and stop dependent admission when required. Do not clamp to the reservation or manufacture headroom. This is a failed bound requiring review, not proof the configured ceiling held. Currency conversion/rate-refresh/residual exposure policies need approved production bounds; none is inferred from the owner's routine net funding figures.

## Physical-capacity release

Reserve separate local-worker and possible-remote-execution capacity where necessary. Account/global/provider capacity allocations are atomic with financial admission. Local function/worker concurrency alone does not measure outstanding provider work across instances or after a crash.

Safe release cases are deliberately narrow:

- **Before intent:** a serialized `aborted_unsent` transition wins against the only possible claimant, permanently preventing invocation; release its financial and capacity reservations once.
- **After intent:** release remote capacity only on attributable provider-specific terminal evidence proving that request cannot still execute, or a separately verified provider-enforced execution bound/termination mechanism coupled to effective exclusion of every delayed sender. A local deadline, socket close, provider bill, lease expiration or sampled empty logs is insufficient by itself.
- **Unknown remote outcome:** retain the possible-remote slot. Stop admitting when the finite pool is exhausted and reconcile/escalate. Do not rename it into a free slot after W. Reviewed financial maximum accounting neither proves termination nor supplies new physical capacity.

The local fake provider can issue authenticated synthetic terminal observations to exercise release. No current provider-specific terminal guarantee, hard maximum execution bound, operator override or numerical capacity limit is selected for live use. Reopening a pool through unsupported administrative release is prohibited. Availability/operator cost from conservative holds remains an explicit operating trade-off.

## Customer allowance and content boundary

Use three independent ledgers/state views: provider expense/exposure, customer finite Draft rights, and delivery/Accept outcomes. A grant is not a provider budget. No-charge invitation planning does not imply unlimited attempts, standalone entitlement or zero expense.

The future customer reservation is one per recoverable Draft Action, with at most one final eligible-delivery effect. Job analysis, incomplete output and CV-only output do not deduct a partial Draft. A bundle requires the coherent job summary, tailored CV, cover letter and every explicit employer answer (or an indication that none was requested), correct input/evidence/language/version, applicable support checks and recoverable availability. Honest qualification gaps do not themselves make generation unsuccessful. A provider response or HTTP 200 is not this delivery event.

An authoritative successful opening for review commits the single delivery effect independently of Accept. Duplicate/lost-ack delivery confirmation retrieves the same effect; it does not regenerate. Confirmed pre-delivery cancellation or terminal unconfirmed-delivery closure prevents late debit forever. A separately agreed customer deadline and its start/reset/restore rules are required for that closure; **168 hours is not that deadline**. Defect/wrong-debit/cash remedies remain separate.

The proposed next slice exercises these ordering rules with synthetic result references, including zero real deductions. It does **not** persist real Drafts, jobs, temporary answers or intermediate ingestion content. Consequently it cannot yet provide lost-result recovery or a live delivery effect. Dependent delivery work needs its own approved content-access/retention/recovery contract under #255/#258/#260. Keep the live debit path unavailable until that authority exists; metadata status lookup must not promise the missing content.

## Retention, deletion, keys and stale restore

Proposed access uses separate least-privilege runtime operations and separately authorized reconciliation operations. Runtime can admit and append bounded observations; it cannot perform an arbitrary downward adjustment or erase a hold. Reconciliation sees only necessary restricted linkage/evidence and applies reviewed idempotent commands. Migration privileges are separate. Ordinary diagnostics/support have no direct ledger view, fingerprint, account/provider-request ID or stable linkage. Database errors, traces and exports must obey the same restrictions. Exact SQL role names/field grants are mechanics to verify locally; production elevation/actor authority remains unresolved.

No career text, Profile snapshot/excerpt, job, temporary answer, prompt/result, credential or credential hash enters the ledger. No FK cascade from Profile deletion may silently remove a financial obligation/replay marker. Conversely an unresolved charge is not a justification to retain career content. Account unlinking/aggregation must preserve account/global limits and deletion/replay purpose; opaque IDs remain potentially identifying.

| Clock / lifecycle boundary | Required treatment |
| --- | --- |
| Durable intent + 168 elapsed hours | Immutable per dispatch, trusted elapsed-time comparison, reviewed financial eligibility only. Stage/retry has its own intent but never renews a parent's anchor. No auto purge, release or customer deadline. |
| Deleted career recovery copies | Existing maximum 30 days after successful active deletion; restore/copy must not restart it. This is not a ledger TTL. |
| Post-paid-access saved Profile | Existing 30 days from authoritative end of paid access, with its selected view/export/notice boundary; it does not define never-paid-account treatment or ledger retention. |
| Routine provider-content retention | Existing documented maximum 30 days for the actual applicable provider arrangement; no-training and exception review remain separate. This does not set non-content metadata retention. |
| Detailed ledger, request/evidence/rate records, linkage/fingerprints, keys, replay/deletion markers, metadata backups and adjustment records | Purpose, start event, duration, active-deletion completion and residual-copy expiry remain unselected. No production collection/cleanup can depend on an invented TTL. |
| Admission capability validity, customer recovery/cancel/closure, grant expiry and never-paid account lifecycle | Separate clocks with unresolved numerical values/policies. Existing ingestion's ten-minute signed handoff TTL supplies none of these rights or replay-retention horizons. |

Propose original intent timestamps from trusted DB UTC evidence; clients cannot backdate them. A pre-commit claim timestamp alone does not prove the durable-intent origin. Review must establish at least 168 elapsed hours since durable commit, using trustworthy commit evidence or an immutable conservative post-commit bound. Commit/clock ambiguity leaves eligibility unavailable; the bound delays proof without rewriting or renewing the dispatch's original window. A later lookup/restart cannot become a fresh origin. Clock-health failure, backward movement or untrusted forward jumps cannot authorize early closure. Exact production commit/clock-health evidence and tolerances remain an operating prerequisite; no new clock service or database setting is selected. Synthetic tests inject delayed commit and clock uncertainty.

Compaction must be an explicit reviewed command, with an allowlist of surviving fields and independently retained counted expense/carry. Preserve minimal terminal/deny markers sufficient to reject old Action/stage/dispatch replays and late customer debits. Keep original deletion/intent anchors wherever still necessary. Removing a fingerprint/key is safe only if remaining authority can still reject every old command; key loss or unverifiable binding fails closed.

Marker pruning needs a proof that the whole relevant namespace is durably retired: every accepted capability/request-validity horizon has passed, every entrypoint rejects it, and no delayed sender, old process or admissible restore can revive it. Exact horizons are unresolved. If that proof is absent, synthetic design must show denial/quarantine, not declare pruning safe or retain all detailed linkage forever as an unstated policy. Financial counters/necessary residual identity cannot disappear with row cleanup. New-account recreation cannot inherit or bypass another account's namespace.

**A stale PostgreSQL snapshot cannot prove that it contains every prior intent, deduction, deletion or revocation.** Boot restored managed admission closed and withhold protected result release until current deletion/replay/exposure authority is reconciled and the old system is effectively excluded.
