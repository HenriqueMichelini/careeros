# Local pilot observation and support

This procedure exercises the owner-selected [pilot operations policy](https://github.com/HenriqueMichelini/careeros/issues/291#issuecomment-6645260210) using synthetic accounts, fake providers, a fake notification sink and disposable PostgreSQL. The [engineering contract](pilot-operations-contract.md) records the authority, data and timing boundaries.

## Start the exercise

Install the account schema and the selected managed qualification composition in one disposable schema. The operations observer uses that shared USD ledger and the existing #290 authority. Install operations roles separately from the stop/reopen and financial reconciliation roles. The database owner can bootstrap one existing synthetic operations owner and a distinct ordinary-support identity. Keep the local process and its journal configuration under the fixture operator's control. A participant or support Session conveys no filesystem, reader database or operator capability.

Create an owned private directory with mode 0700 and a new exercise-only 32-byte journal key. Set `CAREEROS_OPERATIONS_JOURNAL_DIRECTORY` to its absolute path and `CAREEROS_OPERATIONS_JOURNAL_KEY` to the hex key through private process configuration. The key stays out of arguments and output. Bind the same directory/key to each enrolled synthetic Store and Harness through `Store.LocalOperations` before accepting a protected operation. The first binding persists in PostgreSQL. A current local path that lacks the binding fails closed for invitations and inference. The journal holds the stop even while the primary store is unavailable or before the stop is replayed after recovery. Use a separate independent destination for served public status.

The operator CLI requires `--synthetic-only`. For database actions it also takes a loopback isolated disposable `CAREEROS_OPERATIONS_DATABASE_URL`, the existing qualified reader role URL as `CAREEROS_OPERATIONS_READER_URL`, the exact installed `CAREEROS_OPERATIONS_NAMESPACE`, and a current process-local `CAREEROS_OPERATIONS_SESSION_TOKEN`. Bootstrap uses the explicit local database-owner role. Example commands operate on configured synthetic fixtures.

```text
rtk proxy go run ./cmd/pilot-operations-local --synthetic-only --action bootstrap --role owner --subject synthetic-owner
rtk proxy go run ./cmd/pilot-operations-local --synthetic-only --action inspect
rtk proxy go run ./cmd/pilot-operations-local --synthetic-only --action status
rtk proxy go run ./cmd/pilot-operations-local --synthetic-only --action fault --kind backup_fault
rtk proxy go run ./cmd/pilot-operations-local --synthetic-only --action ack --id <incident> --revision <revision>
rtk proxy go run ./cmd/pilot-operations-local --synthetic-only --action resolve --id <incident> --revision <revision>
rtk proxy go run ./cmd/pilot-operations-local --synthetic-only --action prune
```

An inspection reads one complete enrolled qualification namespace and observes counts at the recorded sample time. It reports counted conservative exposure, compatible observed usage estimates, supported estimates, reviewed maxima, attributable bills, unknown differences, possible remote occupancy, locally open execution records and exhausted Draft grants as separate measures. The expense figures can overlap. Each amount is an integer in the selected microUSD currency. Extra or unexpected namespaces and incomplete or unavailable samples require explicit review with admission closed. A rolling warning lasts for the original observed crossing episode. A later crossing after an observed recovery below the bound starts a distinct episode. The first known notification attempt anchors its retry schedule. A late poll skips obsolete retry slots. An in-progress or lost-reply outcome remains unknown and issues no retry.

The operations journal records minimized incident references, original timestamps, typed outcomes, owner, response, status and notification revisions. The local sink writes fake notification receipts to the operator command's standard error. The process can run `fault` independently of PostgreSQL, including a declared backup failure. Backup remains unobserved until an explicit declaration. There is no backup freshness or inspection schedule in the code. A fault involving the enrolled managed provider composition pauses its inference until the fault and shared controls are reviewed. An unacknowledged warning reaches the invitation and inference controls at 24 elapsed hours. Acknowledge and resolve record handling. Only separately verified #290 reopening changes the underlying controls to open. A newer incident makes earlier reopening proof stale.

Reservation, durable intent and reconciliation commit the risk observation together with the ledger transition. An enrolled managed process delivers the queued observations as part of the transition and replays any undelivered observations on a later managed request. A durable intent remains an observation even when independent terminal evidence follows at once. The owner `inspect` command refreshes aggregates and drains pending observations when the runtime is idle. The managed auth and authority paths also emit typed faults and ordinary diagnostics. Expected sign-in or grant denials do not create incidents.

Provision a separate random 32-byte offline owner capability with `--action offline-setup` under a current operations owner Session. Keep the hex value in the owner-only `CAREEROS_OPERATIONS_OFFLINE_OWNER_KEY` setting. `--action offline-status` uses that capability with the private journal while SQL is unavailable. Public status and the observer command have no incident-list output. If a required journal write cannot finish, a persistent journal fence preserves the previous authenticated list and denies affected operations. The connected observer adds a shared SQL stop when it can reach the authority. An integrity failure requires independent recovery review before any reopening.

Backup resolution requires the recovery reference from the separately installed synthetic backup verifier for that exact incident. The CLI accepts it as `--reference`. A default installation without a verifier leaves the incident contained. A recorded uncovered absence remains contained through its recorded end. A verified prepared-cover adapter can approve a newly submitted covered plan.

Independent public status uses only confirmed impact, status, next-update and publication timestamps, and a bounded closure limitation. Use `--action publish --impact service --state investigating --next-update <RFC3339>` from the owned local fixture. Use `--action serve-status --listen 127.0.0.1:<port>` to serve `/status/en` and `/status/pt-BR` independently of the application and database. Publish at the actual next-update deadline even when the investigation wording remains unchanged. `publish-recovery` requires the current ordinary verified #290 recovery receipt and a current operations owner. If independent gateway completion still requires separate evidence, continue reporting the confirmed state. Configure the synthetic pilot UI with `VITE_CAREEROS_PILOT_FAKE_SUPPORT_EMAIL` using a fixture `.invalid` address and `VITE_CAREEROS_PILOT_STATUS_ORIGIN` using the independent loopback origin. Missing channels show as unavailable. The UI attaches no career content and provides no access incentive for feedback.

## Rehearse support, rights and absence

- Henrique checks the private inbox every calendar day, including weekends and holidays. The internal first-response target is 48 elapsed hours from actual receipt and requires a substantive reply. Acknowledging a report and responding substantively are separate. Use the ordinary one-hour weekly support/admin allowance to assess synthetic workload. When routine work exceeds that allowance, pause new invitations and review. Separate incident work retains its own procedure.
- For ordinary product, account, billing and voluntary feedback, strip full CV/Profile attachments before intake, preserve the necessary message and include only a necessary small customer-supplied redacted or synthetic example. `intake` accepts the typed JSON message and its original `receivedAt` time on standard input. The case stores intake time independently. The first-response target starts at receipt. `case` reads an authorized case by ID. `case-update` accepts `--kind respond`, `close` or `review` and a JSON object with the response only when responding. Review the necessity of open cases weekly. Retain diagnostics from their original event for seven elapsed days, and ordinary cases from their original closure for thirty. Repeated closure preserves the first closure timestamp. Run `prune` as part of the local review. `case-hold` records a restricted purpose and review date. `case-hold-retire` explicitly releases that separately reviewed hold for subsequent pruning.
- Route rights requests, privacy/security incidents, financial/fiscal evidence, deletion records, replay evidence and reconciliation to their existing separately authorized procedures. Ordinary intake cannot classify those requests as product support. Preserve the available independently authorized retrieval, export, deletion and status experiences. No ordinary TTL transfers to those separate purposes.
- Before a synthetic absence, record whether prepared cover exists and whether an incident/rights owner can act. Submit the window, next-update time and coverage facts to `--action absence` over standard input. Missing cover pauses invitations, activation and inference before the absence and publishes a next update. If no incident/rights owner is available, record no active pilot through the gap. Preserve the original grant and lifecycle clocks.

The release evidence covers local behavior only. Delivery to an actual mailbox, recipient-copy expiry, staffing coverage, privileged MFA/recovery, backup procedures and hosted controls still need separately authorized evidence.
