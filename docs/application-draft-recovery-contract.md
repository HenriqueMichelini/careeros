# Application Draft recovery contract v1

This freezes the local controlled-provider interface for [#281](https://github.com/HenriqueMichelini/careeros/issues/281), on cumulative base `44f2d556d25bb1225d45f526e1809dc5295616d2`. It is a source contract, not a second ticket tracker or evidence of passing behavior. Its composition remains closed unless an authenticated service, PostgreSQL repository, trusted decision adapter and in-memory controlled provider are explicitly supplied. No environment or hosted Function enables it.

## Retained classes and readers

`draft-recovery-v1` admits only the exact job posting/analysis, application-only answers/confirmations, selected source identifiers, immutable Profile/input/language/generation/review version binding, required support snapshots and one coherent complete bundle. Job source is retained once. Support references use exact UTF-8 ranges into that source. The bundle freezes the original output identity/signature; later Profile changes cannot reconstruct or replace it.

No prompt history, request/response buffers, partial generation, full duplicate Profile/repository source, provider credential, customer key or arbitrary opaque extension object is retained. Review/Accept is a reserved retained-data class, not an implemented write or settlement operation in this slice. Non-content Action/status/replay evidence is separate from purpose-content rows. New tables grant no access to existing AI-ledger runtime roles.

`Input` names the approved full Profile ID/revision, exact job and optional versioned analysis, application-only answers/confirmations, selected fact IDs and language. The repository reads the current saved Profile under existing account/session locks, compares the explicit source precondition, and freezes a keyed input binding. The provider receives that source transiently; the repository does not retain another raw Profile document.

`Bundle` contains role summary, resume, final cover letter including frozen signature, employer answers (`complete` with required-answer correspondence, or explicit `none_requested`) and the required resume/artifact support snapshots. Stable claim/fact/job references, generation/review versions and language belong to the same Action/version. Readiness requires complete checks, exact field/claim coverage, valid career/job references and no uncertain/unsupported claim or unresolved concern. Parseability, HTTP 200 and a `complete` flag alone are insufficient. The controlled provider is a fixture, not evidence of model quality, A4 eligibility or live provider behavior.

## Repository and HTTP interface

- `Create(principal, creationKey, Input)` authenticates and freezes a content-free original-authority guard, opens the actual shared `aicontrol` Action, and atomically records its purpose-content plus durable one-use generation witness. The restricted ledger and content commits are deliberately separate. A gap status joins the frozen guard to the same shared Action/original admission, with no provider/check execution; an explicit identical POST can claim the still-unclaimed first witness once. A changed authority epoch/terminal fence cannot be rebound after apparent restoration. A replay with the same binding returns its existing status, including after a lost create response. Different input under the same key conflicts. Only the winning generation-witness creation may invoke the controlled provider; pending/unknown/incomplete witness replays never invoke it again.
- `Prepare(principal, creationKey, Bundle)` validates the candidate, invokes the injected independent completion/check outside every database transaction, binds its exact original-posting/candidate/input digests and explicit required-answer correspondence, and returns a private sealed `Publication`. Omitted optional analysis cannot mean no employer answers.
- `Publish(principal, creationKey, Publication)` validates the sealed whole bundle and atomically publishes it with owner, full Profile source, frozen input/language/contract versions and the current trusted fences. A changed Profile before commit rejects publication. An already committed equal publication is idempotent; another payload/version cannot overwrite it. No database transaction spans controlled generation or the independent completion/check callback. Pure schema/integrity verification on reads does not re-run either callback.
- `Status(principal, creationKey)` and `Read(principal, creationKey, version=1)` are provider-free. They return the exact stored Action/version and bundle. Retrieval never supplies generation authority. A later Profile change is disclosed as historical; it does not mutate the frozen source meaning.
- `Cleanup(principal, Action)` removes only purpose-content already made inaccessible/queued by a winning closure/deletion/retention fence. It preserves non-content replay/status evidence, independently authorized Profile data and provider-expense/capacity records. It is not the full deletion lifecycle.

HTTP routes are authenticated `POST /api/drafts`, `GET /api/drafts/{creationKey}`, and `GET /api/drafts/{creationKey}/versions/1`, with the existing account consistency, Origin and CSRF rules. The explicit account Function alias reaches the same router. Missing injected dependencies fail closed. No client-supplied owner, decision, publication payload, delivered flag, version, provider credential, attempt or dispatch identifier is authority. Publication is server-to-repository only.

## Trusted decisions, ordering and clocks

The injected decision adapter runs inside the repository transaction after the existing account/session lock, using trusted PostgreSQL time. It must serialize its grant/deletion mutations using that same account lock, monotonically advance its epoch for terminal authority changes (including later restoration), and revalidate any later blocking fence. The original epoch is retained before the separate ledger admission, and a committed generation witness is never released for resend. The adapter supplies generation/publication/read rights, grant expiry, deletion/revocation outcome and whether an already complete delivery is authoritatively confirmed. It cannot derive those rights from a browser assertion. This slice does not integrate real pilot grants, record opening/confirmation, consume allowance or persist human Accept.

The customer deadline is exactly 30 elapsed minutes from original durable admission. Creation replay, status, reload and any future permitted Retry cannot extend it. Earlier grant expiry or authoritative pre-delivery cancellation/revocation/deletion closes an undelivered Action. Closure denies result access, queues purpose-content deletion, and cannot be revived by late publication. The corresponding customer allowance outcome belongs to its later authority slice; no billing receipt is invented here. Provider expense/capacity does not automatically release.

Already confirmed complete delivery is not erased by later cancellation/deadline. Its retained access is bounded by 30 elapsed days after original grant expiry and any earlier deletion/read fence. That window is not measured from readiness or publication. Delivery confirmation and closure ordering is an injected authority contract here, not its later implementation.

Lock order is account/session, injected authority, Action/content. Publication rechecks session, trusted time, injected fences and full Profile source after later locks. Both publication-first and fence-first schedules are verified. Response bytes are written while the final read authority transaction is held, so a fence that wins first cannot leak a retained result through a check/write gap.

The repository checks the locked shared Action before creating a generation witness and when preparing, publishing and reading a result. A shared cancellation closes the undelivered recovery and preserves the ledger's terminal state and exposure records. A temporary denial from the final read decision withholds content while preserving the exact stored bundle for a later authorized read.

## Browser and downstream handoff

The explicit local source mode `VITE_CAREEROS_DRAFT_RECOVERY_MODE=1` uses the authenticated account UI and the injected controlled HTTP composition; no production Function mounts the new router. The actual React recovery view stores only an opaque account-scoped creation key. Reload/reopen uses GET and exact version values, never AI. It displays every required artifact, support snapshot, language, source revision and Action/version. Pending, failed, closed and unavailable content are distinct; it makes no durable-content claim for partial/unknown generation. Temporary content is not saved into Profile, and previous accepted browser work is not overwritten by recovery failures or new candidates.

A scoped exact-version GET reporting `draft_not_found` for an opaque key without an established Action allows a deliberate corrected submission on that same key. The server continues to enforce binding conflicts and the one-use witness. A generic 404 keeps the outcome uncertain.

The editor holds user-entered wording in account-scoped memory for the current document, including during same-account reauthentication. Original job and answer context appear inside the authorized read-only bundle. Authentication denial, access denial and a confirmed account mismatch withhold the current and previous protected results. A different account starts with its own editor and recovery key. Outstanding responses from a previous account cannot restore its protected view.

Managed generation/grant integration, authoritative opening/allowance settlement, human per-artifact review/Accept persistence, historical export and full deletion orchestration consume these interfaces in their own slices. This local implementation does not activate those operations or authorize provider access, hosting, real grants, operational recovery, deployment, publication or launch.


## Validation and source-text compatibility

The completed cover letter includes the original app-owned trimmed identity/signature. Its canonical completion uses the existing browser trim/whitespace set and strict `<400` completed-word limit, including U+FEFF/U+0085 distinctions; the new reader does not rewrite stored wording. Resume completeness uses the same whitespace splitting with its existing `<=400` bound. The legacy raw handler keeps its existing trim/count behavior. Shared structural validation was extracted without changing that path. A five-case Go/TypeScript fixture corpus checks ordinary 399/400 and both Unicode boundaries.

The independent completion adapter is trusted code, not a browser flag or a generic live semantic verifier. This slice provides controlled fixture evidence for complete correspondence; it does not assert arbitrary-job/model quality or A4 layout. The stored snapshot includes the exact required-answer inventory even when optional job analysis was absent. Source-backed career claims cannot become ready merely by marking the whole resume nonfactual or referring only to the employer posting; structural headings may legitimately be nonfactual.

Physical PostgreSQL crash/restart and a fresh server process are tested in an owned private fsync/WAL-enabled cluster with a synchronized append-only generation/check witness. This is local product recovery proof, not authorization or evidence for hosted operational restoration. The browser harness uses actual React, Vite proxy, authenticated Go router and PostgreSQL; it observes and deliberately loses a real committed response, without replacing server DTOs. Test-only loopback controls and synthetic grant/delivery decisions are not product/operator endpoints.
