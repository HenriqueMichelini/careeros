# Local never-paid lifecycle and cleanup

The [frozen contract](never-paid-cleanup-contract.md) links the exact owner-selected #289, #258, #288, #281, #285/#286 and #283 policies. This source is exercised with synthetic accounts, fake recipient/provider callbacks and disposable PostgreSQL. It neither installs a scheduler nor enables actual email, provider disposal, participant cleanup, hosting or recovery service opening.

## Clocks and bounded work

`NewLifecycleWorker` is explicitly code-injected. `Run(ctx, limit)` accepts 1–100 accounts, scans oldest-checked accounts first and handles at most 16 source Profile identities/undelivered purpose records per account. There is no HTTP mutation route. Account/pilot authority, purpose/shared Action and allowance locks precede the applicable trusted database clock decisions. No inference or email callback runs inside a transaction.

The earliest known scheduled expiry/effective early access end starts the selected 30 elapsed days of retained read/export. Temporary suspension preserves original clocks. An inherited revoked grant with unknown effective end gains neither a timestamp nor a new window. At the strict end of the known retrieval window, the worker inventories both the canonical Profile and retained Draft sources, including content whose canonical Profile row is absent. It commits existing per-Profile deletion tombstones and terminal fences before bounded primary removal. It preserves sign-in, finite original grant history and prior consumed delivery effects. Replacement Profile identities and independently authorized data are not deleted by replaying an older Profile/pruning fence.

Undelivered purpose cleanup observes the original customer deadline/earlier terminal event even without an authenticated status GET. It locks purpose/shared/allowance rows, rechecks trusted time and removes only terminal-undelivered input/bundle/review content. The original delivered effect remains. This path never modifies dispatch/allocation/observation/evidence/scope amounts, remote occupancy, local callback leases or input keys. Customer release is not provider termination.

`cmd/lifecycle-local --synthetic-only --limit 10` is normally buildable. It accepts only `CAREEROS_LIFECYCLE_LOCAL_DATABASE_URL` pointing to a literal loopback `*_test` database, with allowlisted routing options. It does not migrate/provision a database or construct an email transport. Its output reports the bounded batch; failure returns an error while durable per-operation status/fences remain available. Hosted scheduling and recipient operations require separate configuration and authorization.

## Notices, unknown outcomes and metadata reads

`GET /api/lifecycle/status` and the account Function alias are owner-bound, freshly authenticated metadata readers through the actual outer HTTP write. Reading status starts no job, cleanup, email or inference. Due in-app notices can be derived from trusted original clocks before a worker has queued email, so missing scheduler configuration is not mistaken for a new retention period.

Expiry and seven-days-before-removal notices retain stable identity and original due/removal timestamps. The email handoff records a durable `sending` intent before the code-owned callback. A crash or ambiguous outcome is `unknown` and never automatically resent. Known failures allow at most three attempts, with eligibility at original due time, +1 hour and +24 hours; no retry extends content retention. Failure/unavailability/unknown remains visible in-app with a persisted operator signal. That signal is a local record, not proof an operator notification or account email was delivered. The default CLI has no recipient adapter and reports email unavailable.

Metadata authorization is separate from canonical career-read eligibility. A valid session whose current Profile is fenced/unreadable can still inspect lifecycle metadata. The `careerReadAllowed` observation guides the Profile UI; it is not a capability authorizing later requests. Those requests retain their own current fences. AccountGate does not misclassify a legitimate career 403 as a lost sign-in. It withholds protected copies and pending merged-recovery downloads while retaining opaque keys and independently entered same-owner work for authorized recovery. Activation remains deliberate; its subsequent focus/session check performs GETs only.

Only trusted known content-window expiry invokes the existing deletion invalidation signal, canceling old same-owner export/Save/AI/editor callbacks. Ordinary grant access end still preserves the selected 30-day read/export period. An old Profile A fence does not represent deletion of valid Profile B. Already customer-held downloads are outside central control.

## Invitations and active Profile provenance

Never-activated invitation expiry/early revocation denies activation immediately and queues invitation-only payload/clearance removal. The worker clears duplicated invitation identity and eligibility result/check/operator fields while preserving independently authorized sign-in identity/content. Minimal invitation ID/original expiry/fence/cleanup markers survive explicit reissue. Reissue receives a new identity/expiry and requires fresh clearance; old markers do not revoke a different new invitation/grant. A restored old identity cannot become active merely because mutable invitation fields reappear. No 14-day grant or post-grant career-content window starts from an unused invitation.

Explicit Profile edits and `applyAccountRetention` remove excerpt payload with no active/current supporting fact reference. Removing a detail also removes its affected shared excerpt, retaining other facts and invalidating affected support/links. Go independently rejects invalid retained evidence on Save. The worker repairs older orphan evidence at a new canonical revision; it preserves untouched raw value subtrees, numeric lexemes, Unicode/NUL and qualifiers instead of round-tripping through `float64` or a view projection. Unchanged cleanup is byte-idempotent. Historical links alone retain no excerpt payload.

This is active Profile cleanup, not semantic text matching across all stores. It does not delete unrelated historical Drafts by matching words, normalize unrelated facts or promise removal of every duplicated mention. Existing full Profile/account deletion remains the separate #288 contract.

Minimal pruning markers contain only owner/Profile/excerpt IDs, old/new canonical revisions and original removal/recovery-copy anchors. They deny a reappearing older canonical Profile revision; Save also refuses reintroducing the retired excerpt identity. Current/replacement identities remain independent. `ExportProfilePruning`/`ApplyProfilePruning` on the existing independently keyed deletion-recovery capability seal/reapply that metadata, with no Profile payload or service-open step.

## Residual and recovery boundaries

Recovery-copy obligations use the original durable fence plus **720 elapsed hours**, never a cleanup retry/restore/copy time. `removedAt` separately records primary completion. Recipient deadline is deliberately NULL: no 30-day recipient disposal guarantee is selected. Deadline expiry reports overdue/not-verified, never automatic erasure success. Excerpt pruning and unused invitation metadata expose the same bounded recovery-copy distinction without inventing a career-content retrieval period.

An optional `SyntheticResidualObserver` is code-injected only for a disposable `*_test` database. It receives minimal obligation metadata outside a transaction and records bounded pending/failed/verified fixture evidence with immutable IDs/revisions and changed-content replay rejection. No real recipient validation contract is supplied; absent/erroring proof leaves the outcome unverified. A controlled fixture proof is not universal provider/recipient erasure or legal sufficiency. Financial/capacity/customer state is untouched.

`ExportLifecycle`/`ApplyLifecycle` add a separate domain-separated sealed metadata handoff on the existing independently owned deletion key. It preserves original notice identities, unknown send intents/attempt counts, cleanup bindings, residual evidence/clocks and old invitation denials. Apply requires corresponding original deletion operations for residual/cleanup parents and does not open service. Older metadata cannot reset unknown intent, reduce a newer evidence revision, replace immutable replay content or extend copy deadlines. Apply the independently surviving deletion and pruning fences before access; this is a bounded local interface, not proof current authority has survived a hosted restore.

Essential expense, remote holds, replay, deletion/customer-terminal markers and keys have no automatic content TTL. The worker does not invoke financial compaction or key retirement. The separately reviewed #283 capabilities remain authoritative. New metadata tables deny PUBLIC and inherited AI-ledger role access. The bounded `careeros_invitation_denied` predicate also gates the shared kernel's direct grant query when older mutable active fields reappear. All boolean predicates are schema-qualified in a validated owning schema, with fixed `pg_catalog, pg_temp`, PUBLIC execution revoked and narrow EXECUTE grants; they expose no raw marker/content/identity rows and perform no writes.

## Verification scope

Real React EN/PT cells run through Vite, authenticated Go and private PostgreSQL; their clock/pending-checkpoint transitions are test-only. A separate fsync-enabled PostgreSQL immediate restart and fresh child process compares exact metadata bytes and a durable callback witness. This is distinct from merely reconstructing a Harness and establishes no hosted recovery or actual provider/recipient operation.

The full Go suite and default vet retain inherited failures. Final evidence must report their exact failure sets, scoped exceptions, optional/helper skips and all source bindings.
