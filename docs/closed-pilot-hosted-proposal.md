## Separately authorized verification request

Submit the completed table and measured evidence plan to the owner before opening a hosted configuration step. Separate permission to configure a closed synthetic candidate from permission to verify it. Provider charges, real grants, participant communication or admission, and production activation each require their own decisions. The verification proposal is conditional on a pinned source/configuration, exact isolated test scope and an approved capped time/resource envelope.

1. Inspect the exact hosted configuration, artifact digests, migration and role receipts with content-free metadata. Demonstrate a missing connector or mismatched configuration denies before accepting work and never falls back to v1 or renders a SPA success for an API failure.
2. Use authorized synthetic identities to check exact HTTPS origin, redirects, OAuth state/PKCE, multiple secure host-only cookies and CSRF. Compare authorized and unauthorized Account, Profile, rights, direct aliases and closed managed paths. Check absence of invitation/activation, managed dispatch and provider fallback. Measure per-request boundaries against selected limits.
3. Check startup/readiness degradation on unavailable storage, route bounds and remaining safe rights/status handling. Verify the app and separately approved status/notification seams with no real participant contact or hidden sends. Preserve existing independent provider uncertainty and cost accounting.
4. Exercise only the authorized scoped closed recovery procedure. Pin exact backup/restore identities and time bounds, reconcile current versus old authority, and demonstrate old-system exclusion before separately verified reopening. Record unavailable evidence or observed fail-closed behavior against each selected requirement.
5. Compare against the approved cost and configuration envelope. Preserve the report and explicit owner acceptance decision. Keep controls closed independently of successful verification until any later activation decision.
