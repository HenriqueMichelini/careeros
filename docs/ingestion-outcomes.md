# Profile ingestion claim outcomes (#40)

The stateless ingestion handler accepts the browser's validated canonical Profile snapshot alongside its compatibility view. Their values and entry identities must agree. It sends only relevant comparison facts and their employer, role, project and period identity context to reconciliation. Stable references identify the same Profile, fact ID and revision; the browser validates them again against the review snapshot and rejects stale apply.

Each returned claim has one outcome: `change`, `exact_duplicate`, `overlap`, `additional_support`, `contradiction`, `correction`, `clarification`, `unsupported` or `unresolved`. Outcomes carry a reason, related stable facts, related submitted statements and indexes into the actual validated patch. Missing or malformed outcomes become unresolved; a missing patch never establishes a duplicate. Operation-only transitional provider responses receive conservative server accounting. Clients without a canonical snapshot cannot establish stable saved-fact duplicates.

Only identical original wording or the pinned JavaScript/Javascript and TypeScript/Typescript aliases can establish exact equivalence. Generated summaries, related technologies, abbreviations and similar employer names cannot establish it. Meaning qualifiers and owner/period context must remain compatible. Unrecognized identity wording asks for clarification. Related facts in review expose their original value, identity context, stable ID/revision and accepted excerpts; a pointer establishes traceability rather than semantic truth.

An `evidence` operation can attach explicitly accepted support without changing the existing field value. Apply revises the stable fact, keeps earlier active support and preserves qualifiers and unrelated evidence. Edited evidence-only values are rejected. Wording updates and evidence-only updates to the same field require separate reviews. Contradictions and correction/supersession candidates carry no applicable changes: competing statements and accepted support remain visible until the user resolves them deliberately. Processing and inspecting the ledger do not save Profile.

`coverage` reports valid and invalid returned claims, never semantic discovery completeness. Reaching the 30-claim ceiling reports possible capacity exhaustion. Invalid extracted claims retain bounded unvalidated wording, a resolved original excerpt when available, and numbered localized reasons. Unresolvable sources have an explicit fallback and shortened wording is disclosed. Ordinary provider explanations have localized reason categories; source-specific comparison detail is separately labeled in the submitted text’s language. An invalid result or provider truncation preserves the input for deliberate retry. Continuation and clarification conversations remain #41/#42 work.

The ledger and complete paste remain transient. Durable saves retain only accepted fact changes and their accepted supporting excerpts, through the existing atomic browser-local transaction. There is no database, source archive, automatic retry, provider fallback or new provider call. Controlled handler/browser verification does not establish live-provider extraction quality or deployed behavior.
