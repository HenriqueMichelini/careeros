## Safe provider-backed check procedure

1. Use an explicitly approved, minimized **synthetic** Profile and posting. Before each real request, inspect the exact Go-to-OpenAI payload for that workflow against the approved fields and stop if excluded fields would be sent. The Profile review and Application Draft contracts currently include the full Profile, so use a synthetic Profile containing only approved non-sensitive values; do not use a real Profile as a shortcut. Record only a preflight pass/fail and field names, never the text.
2. The authorized tester enters a dedicated test OpenAI key directly into the app UI in each accessible Netlify environment. Do not transfer the vault key through this agent, a command, a file, a URL, Netlify configuration, or a diagnostic log. The browser stores the entered key locally; use an isolated browser profile and clear that profile after testing. Make one deliberate request per workflow and environment, without automatic retry. Ask the key owner before any additional billable attempt.
3. In browser DevTools Network, record the request's HTTP status, total browser duration, `Cache-Control`, Netlify cache status and request ID. The browser duration includes network and browser overhead; it is not Function execution time. Never export a HAR containing request headers or bodies.
4. An invited Netlify team member opens the matching deploy's Function logs **read-only**, filters to the request time and workflow, and records only status, outcome, and the handler's `duration_ms` (or Netlify invocation duration) plus the deploy ID. Handler duration includes validation, OpenAI work, and response encoding. Review the actual log lines for content or key leaks without copying them into release evidence. A build log is not a Function log.
5. Record provider duration separately only when a verified server-side measurement of the outbound OpenAI exchange is available. The current handlers log total Function duration but no provider-specific duration, so mark that field **unavailable** for this baseline; do not subtract browser and Function durations or relabel local-provider timing as a deployed measurement. Add metadata-only outbound timing before a later ticket requires a numerical provider duration.

Keep one metadata-only evidence row per workflow and environment in `docs/release-evidence/` with date, environment URL, deploy ID, full revision, request ID, HTTP status, error category or result-shape pass/fail, cache status, browser milliseconds, Function milliseconds, provider milliseconds or `unavailable`, exact-payload preflight pass/fail, and Function-log privacy review pass/fail. Never store keys, headers containing keys, Profile or posting text, generated content, prompt bodies, or raw logs there. Any factual review of generated output should be summarized as pass/fail and issue categories; retain raw output only in the tester's approved private review surface.

**Current gate:** the two environments load over HTTPS, run the same identified build, and pass the credential-free Go route and `no-store` checks. Provider-backed checks and actual Function-log review belong to the later workflow release checks and have not been performed here.
